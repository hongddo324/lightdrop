# LightDrop: 화면 → 카메라 오프라인 파일 전송

인터넷도 케이블도 없이 **한 기기의 화면**에 컬러 애니메이션 코드를 띄우고 **다른 기기의 카메라**로 찍어서 파일을 옮깁니다.
`lightdrop.html` 파일 하나만 있으면 됩니다. 외부 라이브러리나 서버는 필요 없습니다.

## 설계

| | QR (버전 40, L) | LightDrop v2 (128×128, 8색) |
|---|---|---|
| 칸당 비트 | 1 (흑/백) | 3 (R·G·B 채널마다 1비트) |
| 프레임당 실제 데이터 | 최대 약 2.9KB | 약 4.5KB (160격자면 7.2KB) |
| 놓친 프레임 | 해당 조각이 다시 나올 때까지 기다림 | 분수 코드: 구간마다 아무 symbol이나 K+2개 남짓 받으면 복원 |
| 찢긴 프레임(화면 갱신 중 촬영) | 버림 | 찢긴 선이 지나는 **띠 하나만** 버리고 나머지는 사용 |

1. **컬러 3채널 = 3배 밀도.** 받는 쪽은 채널별로 주변 7×7칸 평균을 기준값으로 써서, 밝기 얼룩·비네팅·색 번짐이 있어도 판별합니다(데이터를 화이트닝해서 주변 평균이 늘 중간값이 되게 함). 기준이 상대값이라 **밝기를 낮춰도** 그대로 읽힙니다.
2. **띠(band) 구조.** 데이터 영역을 가로 띠 3~8개로 나누고, 띠마다 자체 리드-솔로몬 코드워드, symbol 번호, CRC를 둡니다. 롤링 셔터 카메라가 프레임 전환 중에 찍으면 위는 N번, 아래는 N+1번 프레임이 섞이는데, 이때도 경계가 지나는 띠 하나만 잃습니다. 헤더는 세션 내내 같아서 찢겨도 깨지지 않습니다.
3. **구간별 체계적 분수 코드.** 파일을 블록으로 나누고 1024블록씩 "구간"으로 묶습니다. 구간마다 원본 블록을 먼저 보내고, 이어서 "블록 절반의 무작위 XOR" 보강 symbol을 보냅니다. 받는 쪽은 GF(2) 가우스 소거를 symbol이 올 때마다 조금씩 진행하므로, **어떤 symbol을 놓쳤든 K+2개 남짓이면 복원**됩니다(측정 1.000~1.007배). 구간 크기가 고정이라 1GB든 10KB든 메모리와 계산량이 일정합니다.
4. **빠른 수신 파이프라인.** 카메라 프레임 분석은 Web Worker 여러 개(코어 수−1, 최대 4)가 병렬로 처리하고, 한 번 코드를 찾으면 다음 프레임은 이전 모서리에서 미세조정만 합니다(전체 탐색 생략).
5. **큰 파일 지원.** 보내는 쪽은 파일을 메모리에 올리지 않고 필요한 구간만 Blob에서 잘라 읽습니다(압축도 스트리밍). 받는 쪽은 완성된 구간을 Blob(큰 데이터는 브라우저가 디스크에 보관)과 IndexedDB에 저장하므로, **중간에 끊겨도 같은 파일·같은 설정으로 다시 띄우면 이어받습니다.**
6. **눈부심 감소.** 전송 화면은 검은 배경에 코드만 표시하며, 크기(기본 45%)와 밝기(기본 60%)를 조절할 수 있습니다.

## 사용법

1. 두 기기 모두 `lightdrop.html`을 엽니다(Chrome / Edge 권장).
2. **보내는 쪽**: [보내기] → 파일 선택 → [전송 화면 띄우기].
3. **받는 쪽**: [받기] → [카메라 시작] → 코드 전체와 **흰 여백까지** 화면에 들어오게 맞추고 고정합니다. 코드가 작으면 카메라를 가까이(10~20cm) 대면 됩니다.
4. 진행률이 100%가 되면 무결성(CRC32)을 확인한 뒤 [파일 저장] 버튼이 나옵니다.

전송 화면 단축키: `↑/↓` 속도, `+/−` 크기, `[ / ]` 밝기, `Space` 일시정지, `R` 처음부터, `Esc` 종료.

### 큰 파일(수백 MB~1GB) 보내기
- 두 기기를 **거치대 등으로 고정**하세요. 손에 들면 보강 비율을 35~60%로 올려야 해서 느려집니다.
- 보내는 쪽 PC의 화면 꺼짐·절전을 끄세요(전송 중엔 Wake Lock을 요청하지만 OS 설정이 우선할 수 있음).
- 1차 전송이 끝난 뒤 받는 쪽에 **"빠진 구간: 12,57-58"**처럼 표시되면, 전송 화면 아래 입력칸에 그대로 입력하고 Enter → 그 구간의 새 보강 symbol만 반복해서 보냅니다(비우고 Enter → 전체).
- 받는 쪽이 꺼지거나 탭이 닫혀도 완성된 구간은 남아 있습니다. 보내는 쪽에서 **같은 파일을 같은 격자·색상 설정으로** 다시 띄우면 이어서 받습니다. 끝나면 보관 데이터는 자동 삭제되고, 수동 삭제 버튼도 있습니다.

### 잘 안 될 때
- 테두리가 빨강(헤더 실패) → 격자를 줄이거나(128→96) 색상 모드를 4색/흑백으로.
- "띠 a/b"에서 성공 비율이 낮으면 → 초당 프레임을 낮추거나(20→15) 반사·모아레를 확인하세요. 칸 하나가 카메라 화면에서 5픽셀 이상 되도록 가까이 대세요.

### 휴대폰에서 여는 법
카메라는 "보안 컨텍스트"(https:// 또는 PC의 file://)에서만 켜집니다. PC에서는 파일을 더블클릭하면 됩니다. 휴대폰은 다음 중 하나를 쓰세요.
- **(권장)** 이 폴더(`lightdrop.html`, `sw.js`, `manifest.webmanifest`)를 GitHub Pages 같은 HTTPS 정적 호스팅에 올리고, 휴대폰으로 한 번 열어 "홈 화면에 추가"합니다. 서비스 워커가 캐시해 두므로 이후에는 **인터넷 없이** 동작합니다. 받는 쪽은 `…/lightdrop.html#rx`로 열면 바로 카메라가 켜집니다.
- 휴대폰이 **보내는 쪽**이라면 카메라가 필요 없으니 아무 방법으로 HTML을 열어도 됩니다.

## 성능 (시뮬레이션 기준, 실기기 측정 아님)
`test/sim.js`는 시간까지 모델링합니다. 60Hz 화면이 위→아래로 갱신되고, 30fps 롤링셔터 카메라(판독 22ms, 노출 8ms)가 찍으므로 찢김·잔상이 실제처럼 생깁니다. 손떨림(느린 흔들림 + 3초마다 큰 흔들림), 원근, 블러, 색 번짐, 비네팅, 노이즈, 카메라 프레임 5% 누락을 넣었습니다. 1280×720 카메라 기준입니다.

| 격자 | fps | 실효 속도 | 비고 |
|---|---|---|---|
| 96 | 20 | 약 43 KB/s | 칸당 6px |
| 128 | 15 / 20 / 30 | 58 / **76** / 57 KB/s | 30fps는 찢김이 많아 오히려 손해 |
| 160 | 20 | 약 120 KB/s | 칸당 3.7px, 좋은 카메라 필요 |

- 이전 버전(v1): 96격자 약 10~14 KB/s, 수신 처리 19ms/프레임 → v2: 수신 처리 10~30ms/프레임(워커 병렬이라 실제 처리량은 몇 배).
- 분수 코드: 30% 손실·늦게 합류 모두 블록 수의 1.000~1.007배로 복원(v1은 K=3000 늦게 합류 시 2.19배). 1024블록 구간 디코딩 CPU는 1GB 기준 총 1~2분.
- **1GB 예상 시간:** 128격자·20fps에서 이상적으로 약 4~5시간, 160격자에서 약 3시간. 실제 카메라·조명에서는 더 걸립니다.

## 솔직한 한계
- 1GB는 광학 전송으로는 여전히 몇 시간 단위입니다. 같은 공간의 두 기기라면 **USB 케이블, 블루투스, 휴대폰 핫스팟(인터넷 없이도 기기끼리 LAN 통신은 됨)**이 훨씬 빠릅니다. LightDrop은 그런 방법을 쓸 수 없을 때(망 분리 PC 등)를 위한 것입니다.
- 받는 쪽에서 보내는 쪽으로 가는 신호가 없으므로, 보강 비율은 손실을 예상해서 미리 정합니다. 부족하면 "빠진 구간"을 사람이 입력해 다시 보냅니다.
- 비슷한 접근의 선행 연구/오픈소스로 libcimbar(컬러 아이콘 매트릭스 + 분수 코드)가 있습니다. 이 구현은 그 계열 아이디어를 의존성 없는 단일 HTML로 다시 만든 것입니다.

## 테스트 실행
```
node test/fountain.js                      # 분수 코드 효율·속도, 다중 구간 왕복
node test/sim.js 128 3 200 4.5 20          # 격자 비트/칸 파일KB 셀픽셀 fps
BRIGHT=0.5 node test/sim.js 128 3 200 4.5 20   # 밝기 50%
node test/make_y4m.js out.y4m 96 3 80 16   # 브라우저 가짜 카메라용 영상(구간 16블록)
```
`make_y4m.js`로 만든 영상을 headless Edge의 가짜 카메라로 넣어, 실제 페이지(워커 4개)에서 7개 구간 수신 → 무결성 검증 → 내려받은 파일이 원본과 바이트 단위로 일치하는 것, 중간에 끊었다가 다시 열었을 때 이어받기가 되는 것까지 확인했습니다.
